# サブエージェント構成

このディレクトリには、本プロジェクト専用の Claude Code サブエージェント定義（`*.md`）を置く。
git 管理されるため、チーム全員が同じエージェントを共有する。

## サブエージェントとは

特定タスク用に、独立したコンテキスト・専用システムプロンプト・限定したツールセットを持つ AI エージェント。
メインの会話（親セッション）を汚さずに、レビュー・調査・修正などの専門タスクを委譲できる。

- 定義ファイル 1 つ = エージェント 1 体（YAML frontmatter + システムプロンプト本文）
- 同名のエージェントがユーザー個人設定（`~/.claude/agents/`）にもある場合、**プロジェクト側が優先**される
- 親セッションには最終報告のみが返る（途中経過はコンテキストに入らない）

## エージェント一覧

| エージェント | model | 書込み | 役割 |
| --- | --- | --- | --- |
| [code-reviewer](code-reviewer.md) | sonnet | ❌ | セキュリティ・バグの厳格レビュー（読み取り専用） |
| [debugger](debugger.md) | 親を継承 | ✅ | バグの診断と修正。Issue# 指定でチケット修正、引数なしで脆弱性監査 |
| [test-writer](test-writer.md) | sonnet | ✅（テストのみ） | Vitest / Playwright のテストコード作成専任 |
| [researcher](researcher.md) | haiku | ❌ | コードベースの高速検索・理解（読み取り専用） |

## 使い方

### 明示的に指名する

```
code-reviewer サブエージェントで今の差分をレビューして
debugger サブエージェントで #12 を修正して
debugger サブエージェントで脆弱性監査して        ← 引数なし = セキュリティ監査モード
test-writer サブエージェントで GanttChart のテストを書いて
researcher サブエージェントで並び替え処理の実装箇所を調べて
```

### 自動起動

各定義の `description` にタスク内容が合致すると、Claude が判断して自動的に委譲する。
（例: 「PR をレビューして」→ code-reviewer が起動しうる）

## 各エージェントの詳細

### code-reviewer — 厳格レビュアー（読み取り専用）

- **チェック観点**: セキュリティ（zod 検証漏れ・インジェクション・秘密のハードコード等）→
  バグ（null 処理・境界値・トランザクション漏れ・循環参照）→ プロジェクト規約
  （`isDone` を使わず `"DONE"` ハードコード等）の優先順
- **出力**: 重要度（Critical/High/Medium/Low）順の表 + マージ可否の総合判定。
  修正案はコードで示すが**適用はしない**
- **ツール制限**: `Edit`/`Write` を除外し構造的に書込み不可。
  `Bash` は `git diff` 用に残している（シェル経由の書込みはプロンプトで禁止し、
  さらに `.claude/settings.json` の `defaultMode: "ask"` が防波堤になる）

### debugger — 診断・修正・脆弱性監査

起動時の入力で 3 モードに分岐する:

| モード | 起動条件 | 動作 |
| --- | --- | --- |
| A. Issue モード | Issue 番号を指定（例: `#12`） | `gh issue view` でチケットを読み、再現→診断→修正→検証。再現手順が不明なら憶測修正せず不足情報を報告して終了 |
| B. デバッグモード | 症状・エラーを報告 | 再現（可能なら失敗する再現テストを先に作成）→診断→仮説検証→最小修正→検証→報告 |
| C. セキュリティ監査モード | 引数なし | 下記参照 |

**C. セキュリティ監査モードの内容**:

1. **依存パッケージ**: `npm audit` 実行 + 主要依存のバージョンを外部の脆弱性 DB
   （GitHub Advisory Database / OSV / Snyk DB / Node.js Security Releases）と照合
2. **コード**: OWASP Top 10 観点で検査 — Prisma 生クエリへの入力混入、全 API ルートの
   zod 検証の抜け、秘密のハードコード、CORS / セキュリティヘッダ、エラー情報の漏えい等
3. **修正範囲の安全弁**: 「依存の安全なバージョンアップ」「明白な脆弱性の最小修正」に限定。
   設計変更を伴うもの（認証の導入など）は修正せず**提案として報告**

**共通の禁止事項**: 再現確認なしの修正 / テストを通すためだけの症状隠し / ついで修正 /
Issue のクローズ・コメント投稿・push（親セッションまたはユーザーに委ねる）

### test-writer — テスト作成専任

- `docs/TEST_DESIGN.md` の方針に従い、既存テストの流儀（命名は日本語「〜こと」形式、
  factories の利用等）を踏襲する
- server: Supertest 統合テスト（`test.db`）/ client: jsdom 単体・コンポーネントテスト /
  E2E: Playwright（`e2e.db`）。純粋関数は単体テストへ寄せる
- **プロダクションコードは変更禁止**。テスト困難な設計を見つけたら修正せず報告に含める
- `dev.db` には絶対に触れない

### researcher — 高速リサーチャー（読み取り専用）

- `model: haiku` で高速・低コスト。「どこで実装されている？」「この処理の流れは？」の
  調査に使い、親セッションのコンテキスト消費を抑える
- ツールは `Read` / `Grep` / `Glob` のみ（`Bash` すら無し）で完全読み取り専用
- 出力は「結論 → 根拠（`ファイル:行` 一覧）→ 補足」に固定。ファイル全文の貼り付けは禁止

## 設計原則

1. **権限は役割の最小限に**: 読み取り専用の役割（reviewer / researcher）からは
   `Edit`/`Write` を除外。書込みが必要な役割も、プロンプトで対象を限定する
   （test-writer はテストファイルのみ、debugger は根本原因の最小修正のみ）
2. **モデルはコストと難度で使い分け**: 定型的な検索は haiku、レビュー・テスト作成は
   sonnet、難度が読めないデバッグは親のモデルを継承（`model` 未指定）
3. **外向き操作はさせない**: push / Issue 操作 / PR 作成はサブエージェントに持たせず、
   親セッションとユーザーの判断に委ねる
4. **止まる条件を明文化**: 情報不足のチケット、再現できないバグ、設計変更が必要な
   脆弱性——判断が必要な局面では勝手に進まず報告して終了する

## エージェントを追加・変更するには

1. このディレクトリに `<name>.md` を作成（または編集）する

   ```markdown
   ---
   name: my-agent            # 小文字ケバブケース
   description: いつ使うかを具体的に書く（自動起動の判断材料になる）
   tools: Read, Grep, Glob   # 省略すると全ツールを継承
   model: sonnet             # 省略すると親のモデルを継承
   ---

   （システムプロンプト: 役割・手順・出力フォーマット・禁止事項）
   ```

2. この README の一覧表に行を追加する
3. 通常のコードと同様に PR でレビューを受ける

> 補足: `description` は「いつ呼ぶか」を書くのがコツ。機能説明だけだと自動起動の
> 精度が落ちる。また、読み取り専用にしたい場合は `tools` から `Edit`/`Write` を
> 外すこと（プロンプトでの禁止だけでは構造的な保証にならない）。
